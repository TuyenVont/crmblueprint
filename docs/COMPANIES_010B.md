## Form and validation

Only existing schema fields are exposed:

| Field | Required | Maximum characters |
| --- | --- | --- |
| name | Yes | 200 |
| tax_id | No | 200 |
| email | No | 320 |
| phone | No | 80 |
| website | No | 2000 |
| address | No | 2000 |
| industry | No | 200 |
| size | No | 200 |

Values are trimmed; optional blanks become null. Company name cannot be blank. Email uses the existing Contacts format check. Website must be an absolute HTTP(S) URL with a hostname and without credentials. Non-string field values are rejected. Size remains free text because the schema defines text, not an enum. Length limits are application validation limits, not invented database constraints. The database name non-empty constraint remains authoritative.

The form is responsive, uses accessible labels and field errors, preserves values on validation/database failures, and disables its fieldset/submit while pending. A synchronous submit latch also blocks a second submission before React renders pending state. This prevents duplicate UI submissions; it is not an idempotency guarantee for independently replayed requests. Cancel returns to company detail/list or dashboard for manage-only creators.

## Authorization, workspace and protected fields

Create route/action requires COMPANIES_MANAGE. Manage-only users may create via /app/companies/new: INSERT requests no returned row, and success appears in the form because detail requires COMPANIES_VIEW. Users with view/manage are redirected to the created company's detail.

Edit render and mutation require COMPANIES_VIEW plus COMPANIES_MANAGE. The mutation checks the company's accessibility first, then repeats workspace/id filters on UPDATE. Invalid/missing/foreign IDs have the same unavailable outcome, and no raw database messages are returned. RLS also handles permission revocation or concurrent deletion. Anonymous requests follow existing getAppContext login redirection.

Every operation resolves workspaceId exclusively from the authenticated server app-context. Browser URL, form, hidden fields and previous action state cannot override it. The eight-field validator output is the only payload copied into mutations; create adds server workspace_id. IDs, owner_user_id, timestamps, created_by and relationship values are ignored. Defaults/triggers manage IDs/timestamps; ownership defaults to null on create and is preserved on edit. No company_contacts query or write occurs in the edit loader or mutation.

Successful changes invalidate Companies list/detail/edit. Edit also invalidates Contacts list/detail cache paths because those views can show company names; Contacts source and relationships are untouched.

## RLS blocker and migration

Existing companies_manage_authorized requires COMPANIES_MANAGE for INSERT/UPDATE. The 010A restrictive policy requires COMPANIES_VIEW only for SELECT. Direct SQL proved that an UPDATE with no WHERE/RETURNING bypassed SELECT policy evaluation and let a manage-only user update companies. The new regression test failed before the migration with 'Manage-only bulk UPDATE bypassed view permission'.

Migration 20260916001200_companies_update_view_guard.sql adds one restrictive UPDATE policy, requiring COMPANIES_VIEW in USING and WITH CHECK. It composes with existing manage authorization. Manage-only INSERT remains valid; read-only and manage-only UPDATE are blocked. No policies are weakened, and no tables/columns, relationship policies or delete capabilities are added. Apply this migration after 010A and before deployment. Applied only to the local disposable PostgreSQL 14 instance during verification; hosted schema parity/deployment remain unverified.
